1. Executive Summary

Patrons are represented in Salesforce as Contact records keyed by Patron_ID__c. This build adds one new tab to the Contact record — the Exclusion Evidence Gallery — that lists the exclusion images held for that patron in an external AWS S3 bucket, and lets authorised users view, enlarge, download and upload them.

This is a deliberately minimal first cut. S3 is the single source of truth — there is no Salesforce custom object and no mirrored metadata record. The gallery is built directly from the S3 object listing (filename + last-modified date). Image bytes never live in Salesforce Files; they stream through Apex, which is required because AWS Signature V4 request signing must happen server-side (the browser cannot sign a request, and the Named Credential only signs calls that originate from Apex).

Why S3-only? The single biggest effort driver in the fuller design was a custom index object (Exclusion_Image__c) with its fields, layouts, field history, triggers and reconciliation. Dropping it removes ~60% of the build while still delivering the tab, the gallery, view/enlarge, download and multi-file upload. Rich metadata capture, editing and audit are deferred to Phase 2 (§16).

This build is a focused slice of the broader Prevention of Play (POP) program. Facial-recognition export, CID bulk migration, patron-merge transfer, exclusion reports, image removal and persona/jurisdiction access rules are explicitly out of scope and captured in §16.

3. Business Context

Post go-live, excluded-patron profiles are no longer created in the legacy CID system, and Surveillance teams rely on holding multiple patron photos to identify excluded individuals. Images arrive from CCTV, incident reports and Synkros. The Star needs a single place on the patron (Contact) record where authorised staff can see and add the exclusion evidence images that are stored in AWS S3.

This MVP delivers exactly that surface — a gallery on the Contact — without yet building the structured metadata, reporting and lifecycle features that the full POP epics call for. It is designed so those Phase-2 features can be layered on without rework: the S3 key convention (§6) already namespaces every image by patron so a future index object can be reconciled against the bucket.

5. S3 Integration Design

All three operations are plain AWS S3 REST calls issued from Apex against the pre-configured Named Credential. The credential injects the Authorization SigV4 header, host, and region automatically — Apex sets only the path, method, body and content type.

Named Credential
callout:Salesforce_S3_Connection
Auth protocol
AWS Signature V4 (AwsSv4) via IAM Roles Anywhere (X.509 signing cert exchange)
Service / Region
s3 · ap-southeast-2
Auth header
generateAuthorizationHeader = true (platform signs each request)

Operations

#OperationHTTPNotes
LISTList a patron's imagesGET /?list-type=2&prefix=exclusion-images/{patronId}/Returns ListBucketResult XML — parse <Contents> for Key, Size, LastModified. Metadata only, no bytes.
GETFetch one image's bytesGET /{objectKey}Response body is the raw image; Apex base64-encodes it for the LWC. Content type from response header.
PUTUpload one imagePUT /{objectKey}Body = decoded image blob; Content-Type set from the file. 200/204 = success.

Example — LIST response (parsed by Apex)

<ListBucketResult>
  <Contents>
    <Key>exclusion-images/40818053/40818053_20260515T091230Z.jpg</Key>
    <LastModified>2026-05-15T09:12:30.000Z</LastModified>
    <Size>284517</Size>
  </Contents>
  <Contents> ... </Contents>
</ListBucketResult>

Parsed with Dom.Document (namespace-aware). A single LIST returns up to 1000 keys — sufficient per patron for the MVP; pagination via continuation-token is a trivial Phase-2 add if any patron exceeds that.

6. Object Key & Naming Convention

Every image is stored under a per-patron prefix so listing is a cheap prefix query and every object is intrinsically linked to its patron (satisfies the one surviving mandatory link in BR13).

exclusion-images/{PatronId}/{PatronId}_{UploadedTimestampUTC}.{ext}

e.g.  exclusion-images/40818053/40818053_20260515T091230Z.jpg
SegmentSourcePurpose
exclusion-images/Fixed prefix (Apex constant)Namespaces this feature within the bucket; also the security allow-prefix (§11).
{PatronId}/Contact.Patron_ID__cGroups all of a patron's images; drives LIST + access check.
{PatronId}_{Timestamp}.{ext}Server-generated at uploadMatches the BR13 filename pattern patronID_uploadedDateTimeStamp.extension; guarantees uniqueness, prevents overwrite.
The display name in the gallery is the basename after the last /. The original client filename is not preserved in the MVP (it becomes a metadata field in Phase 2).

8. Apex Controller API

One class, three @AuraEnabled methods and a small DTO. Upload is one file per call — the LWC loops over selected files so each upload is an independent transaction (independent heap budget + natural partial-success).

public with sharing class ExclusionImageController {

    static final String NC     = 'callout:Salesforce_S3_Connection';
    static final String PREFIX = 'exclusion-images/';
    static final Set<String> ALLOWED_EXT = new Set<String>{'png','jpg','jpeg','webp'};

    public class ImageItem {
        @AuraEnabled public String key;         // full S3 object key
        @AuraEnabled public String fileName;    // basename for display
        @AuraEnabled public Datetime lastModified;
        @AuraEnabled public Long   size;
    }

    // 1) LIST — metadata only, newest first. Drives the gallery.
    @AuraEnabled(cacheable=true)
    public static List<ImageItem> getImages(Id recordId) { ... }

    // 2) GET — one image's bytes as base64 (+ contentType), for tile/enlarge/download.
    @AuraEnabled
    public static Map<String,String> getImage(Id recordId, String objectKey) { ... }

    // 3) PUT — upload a single image; returns the created ImageItem.
    @AuraEnabled
    public static ImageItem uploadImage(Id recordId, String fileName,
                                        String base64Data, String contentType) { ... }
}
MethodReadsBehaviour & guards
getImagesContact.Patron_ID__cBlank patron ⇒ empty list (UI shows empty state). LIST by prefix, parse XML, sort by LastModified desc. cacheable=true for wire + refreshApex.
getImageContact + keyValidates the key begins with exclusion-images/{thisPatronId}/ before calling S3 (prevents fetching another patron's or an arbitrary object). Returns {data, contentType}.
uploadImageContact + fileRejects extensions/content-types outside ALLOWED_EXT with a clear AuraHandledException. Builds the key (§6), PUTs the decoded blob, returns the new item. Overwrite impossible (timestamped key).
Pattern mirrors the existing PatronImageController in the org (keys off Contact.Patron_ID__c, with sharing, AuraHandledException on non-success) — differing only in that it targets the S3 Named Credential and uses native S3 REST rather than the Patron Image API.

  • Tiles show the image, display filename and formatted date. First batch (≈5) load eagerly; the rest lazily as they scroll into view, to keep the tab responsive.
  • Empty state — when a patron has no images (or no Patron_ID__c), a friendly "No exclusion images on file yet" message with the upload affordance. BR11
  • Loading — spinner while the LIST and per-tile fetches resolve; error — inline message + toast.

9.2 Enlarge viewer BR28 BR29

  • Clicking a tile opens a modal with the full-size image, filename and date.
  • ‹ Previous / Next › buttons cycle through the gallery; ←/→ keys mirror them; Esc closes.
  • Download button converts the base64 to a Blob and triggers a browser download with the filename. BR19

9.3 Upload (single or multi) BR22 BR23 BR38

  • <input type="file" accept="image/png,image/jpeg,image/webp" multiple> — or drag-and-drop onto the drop zone.
  • Client pre-checks each file: format (hard reject non-png/jpg/webp) and a soft <720p warning that never blocks. BR10
  • Each accepted file is read via FileReader.readAsDataURL, base64 stripped, and sent through uploadImage — one call per file.
  • Partial success: results are aggregated and reported — e.g. "3 uploaded, 1 rejected (unsupported format), 1 failed (retry)". Valid images are added even if others fail. Gallery refreshes via refreshApex.

9.4 Accessibility BR31

  • Tiles are real buttons — keyboard focusable, Enter/Space activate; alt text = filename.
  • Modal traps focus, exposes role="dialog" + label, restores focus on close; nav buttons have aria-labels.
  • SLDS components and tokens for consistent contrast; status messages announced via lightning-toast / live region.

14. Testing Strategy

  • Apex — HttpCalloutMock covers: LIST (multi-item XML → sorted items), LIST empty, GET (bytes → base64 + contentType), PUT success, bad-format reject, key-confinement reject (other patron's key), no-Patron_ID__c, S3 4xx/5xx → AuraHandledException. Target > 85% and all branches.
  • LWC — Jest: renders tiles from mocked wire, empty state, enlarge modal open/nav/close, download blob, multi-file selection with mixed valid/invalid → correct partial-success summary, sub-720p warning is non-blocking.
  • Manual (sandbox) — real end-to-end against the S3 bucket via the Named Credential: upload several formats, verify keys, view/enlarge/download, cross-patron key attempt blocked.
